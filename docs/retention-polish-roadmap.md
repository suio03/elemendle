# Elemendle 留存与体验打磨路线图

## 1. 项目目标

保留 Elemendle 现有的“每日猜一个元素”核心玩法，同时让玩家在完成每日挑战后有事可做，并愿意在第二天回来。

目标产品循环：

`每日挑战 → 成绩与知识反馈 → 点亮元素图鉴 → 再玩一局练习 → 第二天回来`

本路线图采用渐进式发布。每个版本都必须能够独立上线、独立验收、独立衡量；上一个版本通过验收后，才进入下一个版本。

## 2. 范围边界

### 本轮包含

- 修复统计、连胜、历史记录和模式导航问题。
- 在不改变核心规则的前提下打磨桌面端和移动端每日挑战。
- 增加与每日挑战状态隔离的无限练习模式。
- 增加覆盖 118 个元素的个人图鉴。
- 增加可选的候选元素地图，帮助玩家理解推理过程。
- 增加符合隐私政策的产品事件和可量化验收指标。
- 保留现有多语言路由及旧用户本地数据。

### 本轮明确不做

- 账号系统和云端同步。
- 全球排行榜或竞争性排名。
- 实时多人游戏。
- 付费、订阅或广告调整。
- 同时上线多个互不相关的新模式。
- 大规模后端或部署平台迁移。

## 3. 开始开发前必须确认的决策

### 3.1 数据分析与隐私

`components/analytics.tsx` 已包含 Google Analytics、Microsoft Clarity 和另一个分析脚本，但目前在 `app/[locale]/layout.tsx` 中被注释。FAQ 同时声明 Elemendle 不收集用户数据。

实施前必须从以下方案中选择一个：

1. 保持完全本地化，不统计留存。
2. 只发送匿名聚合事件，不使用用户 ID，并同步修改公开隐私说明。
3. 使用会话回放或持久标识符，同时增加明确披露及必要的同意界面。

推荐方案 2。禁止发送每日答案、具体猜测、自由输入内容、导出数据或稳定用户标识。除非另行完成隐私决策，否则不要启用会话回放。

### 3.2 多语言发布策略

所有新增用户文案必须进入 `messages/` 下的全部语言文件。可以先完成英文交互并确认结构，但不能在其他语言路由中发布缺失翻译的界面。

## 4. 发布顺序

| 版本 | 预计工作量 | 交付结果 |
| --- | ---: | --- |
| Release 1：可靠基础 | 2–3 天 | 状态正确、事件可测、导航真实可用 |
| Release 2：每日玩法打磨 | 3–5 天 | 响应式、易理解、可访问的每日挑战 |
| Release 3：留存循环 | 5–8 天 | 练习模式、元素图鉴和候选地图 |
| 后续实验 | 根据数据决定 | 只在有证据时开发周赛或社交挑战 |

不要把三个 Release 合并成一次大发布。Release 1 用于建立可信基线；Release 2 用于证明核心挑战能够顺畅完成；Release 3 再验证玩家是否愿意继续进入练习模式。

## 5. Release 1：建立可靠基础

### 步骤 1.1：记录当前基线

修改行为前先完成：

1. 运行 `npm run lint` 和 `npm run build`。
2. 单独记录已有失败，避免把历史问题误判为本次回归。
3. 手动验证全新每日局、刷新后续玩、胜利和失败四条路径。
4. 检查英文路由和至少一个非英文路由。

### 步骤 1.2：确定事件协议

建立一个小型分析封装，不要在各 React 组件中直接调用具体供应商。

| 事件 | 触发时机 | 允许的属性 |
| --- | --- | --- |
| `game_loaded` | 每日数据加载完成 | `locale`、`mode` |
| `game_started` | 第一次有效交互 | `locale`、`mode` |
| `guess_submitted` | 提交有效且未重复的猜测 | `mode`、`attemptNumber` |
| `hint_used` | 玩家查看提示 | `mode`、`hintNumber` |
| `game_completed` | 胜利或失败 | `mode`、`result`、`attempts`、`assistEnabled` |
| `share_clicked` | 玩家点击分享 | `mode`、`result` |
| `practice_started` | 创建练习目标 | `difficulty` |
| `collection_opened` | 打开元素图鉴 | `discoveredCount` |

任何事件都不能包含目标元素、猜测元素、自由输入、导出数据或永久用户标识。

如需在不跟踪身份的前提下衡量回访，可以只在本地保存上次游戏日期，并在下次访问时发送聚合的 `daysSinceLastPlay` 数值。

### 步骤 1.3：修复统计和历史记录

修改 `lib/storage.ts`、`types/element.ts` 及对应调用方：

1. 为猜测分布增加第 9 次机会。
2. 让 `updateStatistics()` 返回更新后的统计数据。
3. 游戏结束后立即更新 React 状态，确保顶部、统计弹窗和结果页一致。
4. 胜利和失败都写入历史记录。
5. 使用游戏编号和模式作为逻辑唯一键，避免重复写入。
6. 为所有本地 JSON 解析增加异常和旧结构保护。
7. 保证重复渲染或 API 重试不会重复增加统计。

增加针对连胜跨日、第 9 次猜测、重复结算、损坏存储和 UTC 换日的单元测试。如需引入测试框架，使用 Vitest，并提供明确的 `npm test` 命令。

### 步骤 1.4：建立带版本的数据结构

在加入练习和图鉴前，先定义本地数据版本。迁移逻辑必须：

1. 读取现有 `element-guess-*` 键。
2. 补齐第 9 次猜测和历史记录所需字段。
3. 首次发布时写入新版数据，但暂不删除旧键。
4. 迁移失败时安全回退，不清空用户数据。
5. 将导出格式升级到 v2，同时继续支持导入 v1 文件。

任何迁移都不能静默重置真实玩家的 streak 或历史成绩。

### 步骤 1.5：让模式导航真实可信

`components/game-header.tsx` 中的 Classic 和 Properties 看起来可以点击，但不会切换模式。在 Practice 完成前：

1. 改成单一的已选中 `Daily` 标签，或暂时隐藏未开放入口。
2. 将模式入口与统计、连胜、帮助、数据迁移、语言切换清楚分组。
3. 为图标按钮增加可访问名称和明显的键盘焦点状态。

### Release 1 验收标准

- 第 9 次猜测能够正确保存和显示。
- 一局完成后统计只更新一次。
- 胜利和失败记录刷新后仍然存在。
- 顶部、统计弹窗和结果页显示相同 streak。
- 旧本地数据和 v1 导出文件仍然可用。
- 模式导航中不存在无功能按钮。
- 数据分析方案与 FAQ、隐私说明一致。
- `npm test`、`npm run lint`、`npm run build` 全部通过。

Release 1 上线后至少收集 7 天基线，再判断留存变化。

## 6. Release 2：打磨每日玩法

### 步骤 2.1：分离游戏编排与界面展示

`components/game-board.tsx` 当前同时负责 API、存储、输入、候选提示、计分、动画、结果和结算。只做必要拆分：

1. 每日 API 加载继续由顶层 GameBoard 管理。
2. 将局内状态转换放入专用 hook，例如 `hooks/use-element-game.ts`。
3. `lib/element-game.ts` 继续保存纯比较规则。
4. 只提取职责明确的组件：
   - `components/game-progress.tsx`
   - `components/guess-card.tsx`
   - `components/game-result.tsx`
5. 先用测试锁定现有行为，再调整布局。

本阶段不要引入新的全局状态管理库。React 状态配合现有存储层足够完成目标。

### 步骤 2.2：明确游戏状态

输入框上方显示：

- 每日游戏编号。
- 已使用和剩余次数，例如 `3 / 9`。
- Assist 是否开启。
- 一句简短目标说明。

输入框和提交按钮应靠近最新一条猜测。移动端玩家不应每次都滚回顶部才能继续。

### 步骤 2.3：替换移动端横向表格

当前结果区固定为 8 列和 700px 宽。使用同一份猜测数据实现两套响应式布局：

- 桌面端：空间足够时保留紧凑比较表。
- 移动端：每次猜测显示为一张卡片，主要属性默认显示，次要属性可展开。

所有反馈都必须同时使用颜色和符号：

- `✓` 表示完全匹配。
- `↑` 或 `↓` 表示数值方向。
- `≠` 表示类别不匹配。

390px 宽度下不能出现页面级横向滚动，属性名称也不能被截断。

### 步骤 2.4：改善提示系统

保留现有提示阈值作为默认规则，但让玩家明确控制：

1. 显示下一条提示何时解锁。
2. 提示解锁后由玩家主动查看或关闭。
3. 明确说明使用提示是否影响成绩徽章。
4. 将提示使用情况记录到完成结果。
5. 恢复状态或重新渲染不能提前泄露提示。

### 步骤 2.5：重做结算承接

结算页依次回答三个问题：

1. 我表现得怎么样？
2. 我从这个元素学到了什么？
3. 接下来可以做什么？

具体包含：

- 胜负、次数、时间、streak 和提示使用情况。
- 目标元素及一条来自现有数据集的简短知识。
- 不泄露答案的分享图案。
- 如果 Release 3 尚未上线，练习入口显示为不可点击预告；如果两个版本一同发布，则直接提供入口。
- 下一题倒计时保留，但降为次要信息。

### 步骤 2.6：可访问性与动效检查

1. 为所有图标按钮和提交按钮增加标签。
2. 验证键盘可以操作自动补全列表。
3. 增加清晰的焦点样式。
4. 对彩纸和交错动画支持 `prefers-reduced-motion`。
5. 检查浅蓝文字、红色反馈和半透明面板的对比度。
6. Tooltip 只能作为补充；必要说明不能依赖 hover 才能阅读。

### 步骤 2.7：多语言检查

将无效猜测、重复猜测、候选描述、统计标题和分享提示等硬编码文字全部迁移到 `messages/*/i18n.json`，并验证所有语言文件具有一致的 key 结构。

### Release 2 验收标准

- 每日规则和目标选择逻辑没有改变。
- 390px、768px、1440px 下均无页面横向溢出。
- 玩家可以只用键盘完成整局。
- 无法区分红绿颜色时仍能理解反馈。
- 刷新后正确恢复次数、提示、计时和结算状态。
- 胜利和失败都能正确显示结果及分享内容。
- 所有语言路由均无缺失翻译错误。
- 自动检查和手动 viewport 矩阵全部通过。

## 7. Release 3：建立留存循环

### 步骤 3.1：引入明确的游戏模式

增加只包含 `daily` 和 `practice` 的 `GameMode` 类型。Daily 继续作为默认入口和顶部主要模式。

两种模式必须严格隔离：

- Daily 使用 API 返回的目标、游戏编号、streak、solved count 和每日统计。
- Practice 使用本地选择并保存的目标。
- Practice 不能调用每日完成接口。
- Practice 不能增加每日 streak。
- 切换模式后，两边未完成的游戏都能独立恢复。

只有 Daily 和 Practice 均可用后，才在 `components/game-header.tsx` 增加真实模式切换。

### 步骤 3.2：实现元素挑战与经典练习

Practice 的主要体验不能只是无限版 Daily。默认入口使用 `data/atom.json` 中的结构化属性，在本地生成每轮 5 题的元素挑战：

1. `Who am I?`：给出至少三个属性线索，且组合后只能对应一个元素。
2. `Extreme Element`：从四个候选中判断原子序数、原子质量、熔点或沸点的最大值或最小值。
3. `Odd One Out`：三个候选共享指定属性，玩家找出唯一的例外。
4. Mixed Challenge 按一轮 5 题混合上述题型，也允许单独训练一种题型。
5. 答错不扣生命或提前终止；立即展示正确答案和可验证的知识解释。
6. 当前挑战和最近题目保存在独立的版本化本地存储中，刷新后继续，并尽量避免短期重复。

原来的九次属性对比玩法保留为次级入口 `Classic Practice`。它继续提供 Easy 和 Standard 两种提示节奏，并使用与元素挑战、Daily 均隔离的存档。候选地图仍留在步骤 3.5，不属于 Easy 第一版。

第一版挑战只显示本轮正确数、用时和逐题解释，不增加生命、连胜、排名或长期 Practice 统计。

### 步骤 3.3：增加个人元素图鉴

状态：已实现。

在 `types/progression.ts` 和 `lib/progression.ts` 等独立文件中建立进度模型。每个已发现元素保存：

- 首次发现日期。
- 来源：Daily 或 Practice。
- 最少猜测次数。
- 最佳完成时间。
- 累计成功次数。

图鉴按照周期表位置展示，并显示 `已发现 27 / 118`。未发现元素保留所在位置，但在游戏进行中不能通过图鉴泄露答案。

只有成功完成一局才点亮元素。失败局保留在历史中，但不计为已发现。

元素挑战采用等价规则：只有答对当前题才点亮答案元素；答错后查看解析不会点亮。Daily 和 Classic Practice 猜中目标时点亮。所有更新使用结算事件 ID 去重，刷新结果页不能重复累计。

### 步骤 3.4：连接结算后的下一步

状态：已实现。

完成 Daily 后：

1. 展示本次图鉴更新。
2. 显示总收集进度。
3. 将“再练一个元素”设为主要按钮。
4. 将“查看图鉴”设为次要按钮。
5. 分享和下一题倒计时继续保留，但降低视觉优先级。

完成 Practice 后，主要按钮变为“再玩一个”。

### 步骤 3.5：实现候选元素过滤

状态：已实现。

将候选计算实现为纯函数：

1. 初始候选是全部 118 个元素。
2. 对每一次历史猜测，将该猜测元素与每个可能目标重新执行比较。
3. 只有生成的匹配和方向反馈与玩家已经看到的反馈完全一致时，才保留该候选。
4. 返回候选集合，不修改游戏状态。

每次猜测后显示类似 `118 → 34 → 9 → 2` 的候选变化。可选的迷你周期表淡化已排除元素，并突出剩余区域。

候选辅助必须可以关闭，并记录在结果中，避免混淆辅助和无辅助成绩。单元测试覆盖多次猜测、数值方向、类别匹配和胜利状态。

实现说明：候选地图默认收起，仅在玩家主动打开时记为使用辅助；关闭 Assist 会同时收起地图。该功能用于 Daily 和 Classic Practice，不用于选择题式元素挑战。

### 步骤 3.6：扩展导入和导出

状态：已实现。

v2 导出文件包含：

- Daily 统计和历史。
- Classic Practice 与元素挑战的可恢复进度；按已确认规则不增加长期 Practice 统计。
- 图鉴进度。
- 可以安全恢复的未完成游戏。
- Schema 版本和导出时间。

导入时分别验证每个区块。可选进度数据损坏时，不能连带删除有效统计。

实现说明：重复导入采用幂等合并；图鉴保留更早的首次发现、更好的次数与时间以及来源并集。已完成的旧 Practice 会话不会恢复成当前游戏。

### Release 3 验收标准

- Daily 仍是默认模式，且不打开 Practice 也能完整使用。
- Daily 结束后一次操作即可开始 Practice。
- 两种模式刷新后均能独立恢复。
- Practice 不会改变 solved count 或每日 streak。
- Practice 默认进入 5 题元素挑战，Classic Practice 仅作为次级玩法。
- 三种挑战题型都能由本地数据得出唯一且可验证的答案。
- 每个完成目标只更新一次图鉴。
- 候选算法对所有比较类型均正确。
- 现有 v1 用户数据仍然可用。
- 测试、lint、build、多语言、可访问性和 viewport 矩阵全部通过。

## 8. 数据指标与发布门槛

使用上线前 7 天作为基线，Release 3 后至少观察 2 周。

| 指标 | 定义 | 初始目标 |
| --- | --- | ---: |
| 激活率 | `game_started / game_loaded` | 相对基线提升 |
| Daily 完成率 | Daily 完成数 / Daily 开始数 | 相对提升 10% |
| Practice 启动率 | Practice 开始数 / Daily 完成数 | 至少 25% |
| Practice 完成率 | Practice 完成数 / Practice 开始数 | 至少 60% |
| 7 日回访 | 7 个本地自然日内再次开始游戏 | 相对提升 15% |
| 分享率 | 分享点击数 / Daily 完成数 | 观察，不设强制目标 |

不能只因为猜测次数或停留时间增加就宣布成功；这些数字也可能意味着界面变难。完成率、主动续玩率和回访率才是主要信号。

## 9. 后续实验

Release 3 数据稳定后，每次只选择一个实验。

推荐顺序：

1. Weekly Lab：每周五个短挑战，共用一个周成绩。
2. Periodic Position：根据条件在周期表上选择元素位置。
3. Odd Element Out：从四个元素中找出属性不同的一项。
4. Seeded Challenge Link：无需账号，朋友通过链接挑战同一非每日目标。
5. Classroom Set：由教师或预设主题选择一组元素。

每个实验都必须有假设、唯一主要指标和下线条件。不能因为已经投入开发时间就永久保留表现不佳的模式。

## 10. 每个版本的验证清单

### 自动验证

- `npm test`
- `npm run lint`
- `npm run build`

### 状态场景

- 空存储的新玩家。
- 带现有数据的老玩家。
- 本地 JSON 损坏。
- 游戏中途刷新。
- 第 1、8、9 次猜中。
- 第 9 次失败。
- UTC 日期切换。
- API 失败和重试。
- v1 导入和 v2 导入导出闭环。

### 界面场景

- 390px、768px、1440px viewport。
- 全键盘操作。
- Reduced Motion 设置。
- 英文、一个长文本语言和一个 RTL 语言。
- 胜利、失败、分享、进入 Practice 和图鉴更新。

## 11. 总体完成标准
